# 代码开发标准流程

> 本技能为代码开发的强制流程，每次代码变更任务必须严格按顺序执行。
> 上一步未通过，禁止进入下一步。

---

## 第 0 步 · 先聊再动手

**核心原则**：先讲清收益/代价/风险，用户拍板后才动代码。研究类对话只研究不改码。

**执行要求**：
1. 收到需求后，先分析需求，给出方案
2. 方案必须包含：
   - **收益**：做完能解决什么问题
   - **代价**：需要改哪些文件、影响哪些模块、耗时预估
   - **风险**：可能出什么问题、有没有破坏性、回滚方案
3. 用户明确同意后，才开始动代码
4. 如果只是研究、分析、讨论，不改任何代码

**禁止行为**：
- 未经用户同意直接改代码
- 边聊边改，方案还没定就动手
- 研究对话里偷偷改代码

---

## 第 1 步 · 备份

**核心原则**：改码前必须备份，出问题能回滚。

**执行要求**：
1. 在项目根目录创建 `beifen/` 目录（如不存在）
2. 将整个项目代码打包成 zip，放到 `beifen/` 目录
3. 命名格式：`yyyy-MM-dd_HH-mm-ss_操作说明.zip`
   - 示例：`2026-10-22_14-30-00_用户登录功能.zip`
4. **排除目录**（不打包）：
   - `node_modules/`
   - `.nuxt/`
   - `.output/`
   - `.temp/`
   - `beifen/`
   - `__pycache__/`
   - `.venv/`
5. 备份完成后**自检体积**，确认备份包大小合理（不是空的、不是只备份了一小部分）

**Windows 备份命令示例**：
```powershell
$timestamp = Get-Date -Format "yyyy-MM-dd_HH-mm-ss"
$backupName = "${timestamp}_操作说明.zip"
$exclude = @("node_modules", ".nuxt", ".output", ".temp", "beifen", "__pycache__", ".venv")
# 使用 Compress-Archive 或 7z 打包，排除上述目录
```

**禁止行为**：
- 不备份直接改代码
- 备份包含 node_modules 等大目录
- 备份后不检查

---

## 第 2 步 · 改码

**核心原则**：代码规范 + 全中文注释，模块化设计。

**执行要求**：
1. 调用「代码编写与重构规范」技能，确保代码符合规范
2. **全中文注释**：
   - 每个文件头部必须有中文说明（文件作用、创建人、核心功能）
   - 每个函数/方法上方必须有中文说明（功能、入参、出参）
   - 复杂逻辑必须有中文行内注释
3. **模块化设计**：每个模块负责一个功能，不混写
4. 代码修改必须有明确目的，不做无关改动
5. 改动范围控制在需求范围内，不擅自扩展

**禁止行为**：
- 无注释或英文注释
- 一个文件塞多个不相关功能
- 改了需求之外的代码

---

## 第 3 步 · 启动双端

**核心原则**：改完必须启动验证，不能只看代码不运行。

**后端启动**：
- 命令：`H:\huanjing\python\python.exe main.py`
- 端口：`8000`
- **无热重载**，改了后端代码必须杀干净进程再重启
- 启动日志必须检查无报错

**前端启动**：
- 命令：`npx nuxt dev --host 127.0.0.1 --port 3000`
- **HMR 不可靠**，结构性改动必须杀干净重启
- 启动日志必须检查无报错

**进程管理要求**：
1. 启动前确认 3000/8000 端口未被占用
2. 改了代码后，必须杀干净旧进程再启动
3. Windows 杀进程命令：
   ```powershell
   # 查找占用端口的进程
   netstat -ano | findstr :3000
   netstat -ano | findstr :8000
   # 杀掉进程
   taskkill /PID <进程ID> /F
   ```

**禁止行为**：
- 改完代码不启动就认为没问题
- 旧进程没杀干净就启动新的
- 不看启动日志

---

## 第 4 步 · 浏览器实测

**核心原则**：Playwright 真实交互，不能只看启动成功。

**执行要求**：
1. 使用浏览器控制工具进行真实交互测试
2. **必须包含 375px 移动端布局验证**：
   - 新改动必须完全在界内，无溢出
   - 按钮、输入框、文字不重叠
   - 滚动、点击正常
3. **console 0 error**：
   - 浏览器控制台必须无 error
   - 必须区分错误来源：
     - **本轮引入**：必须修复
     - **既有项**：记录但不阻塞（需告知用户）
     - **测试预期**：测试触发的预期错误，不算问题
4. 测试覆盖核心功能路径，不只是打开页面看看

**测试清单**：
- [ ] 页面正常加载，无白屏
- [ ] 核心功能可操作（点击、输入、提交）
- [ ] 375px 移动端布局正常
- [ ] console 无 error
- [ ] 网络请求无 4xx/5xx（预期除外）

**禁止行为**：
- 只启动不交互
- 不验证移动端
- console 有 error 不处理

---

## 第 5 步 · 白盒审计

**核心原则**：调用 6k 审计技能（src-security-research，Phase 0~6）审改动面，发现漏洞修到 0 才准继续。

**执行要求**：
1. 调用 `src-security-research` 技能
2. 对本次改动的代码进行白盒审计
3. 按 Phase 0~6 执行：
   - **Phase 0**：优先级排序（先看哪类代码）
   - **Phase 1**：建立心智模型（信任边界、数据流、权限模型）
   - **Phase 2**：变体分析（历史 CVE、同模式搜索）
   - **Phase 3**：Sink 逆向追踪（危险 Sink、参数来源、过滤绕过）
   - **Phase 4**：框架专项（Laravel/Spring/Django/Node.js 各框架漏洞）
   - **Phase 5**：深层（竞态、业务逻辑、配置密钥、依赖 CVE）
   - **Phase 6**：验证（输入可控性、过滤绕过、前置条件、影响、PoC）
4. 发现漏洞必须修复到 0 个，才能继续下一步
5. 输出审计结果：发现的问题、修复情况、最终状态

**审计重点**（针对改动面）：
- 输入验证是否到位
- SQL 是否参数化
- XSS 是否转义
- 越权是否检查
- 敏感信息是否泄露
- 错误处理是否暴露细节

**禁止行为**：
- 跳过审计
- 有漏洞不修复就继续
- 审计走过场

---

## 第 6 步 · 逐项验证

**核心原则**：上一项验证不通过，禁止进下一项。

**执行要求**：
1. 按以下清单逐项验证，每一项必须通过：
   - [ ] 第 0 步：方案已获用户确认
   - [ ] 第 1 步：备份已完成且体积正常
   - [ ] 第 2 步：代码规范、全中文注释、模块化
   - [ ] 第 3 步：双端启动无报错
   - [ ] 第 4 步：浏览器实测通过（含 375px、console 0 error）
   - [ ] 第 5 步：白盒审计 0 漏洞
2. 任何一项不通过，必须回去修复，修复后重新验证
3. 不允许"先记着，以后再修"

**禁止行为**：
- 跳过验证步骤
- 验证不通过就继续
- 多项一起验证不逐项确认

---

## 贯穿纪律

### 数据纪律
- 全程只用本地库：`root/root@127.0.0.1:3306/cc_api`
- 测试造数必须可逆
- 收尾时还原测试数据，并核对全库无遗留

### 卡住纪律
- 遇到问题先通报用户，不擅自绕过
- 不改用户没拍板的任何项
- 拿不准的地方先问，不猜

### 收尾纪律
1. 停服务：确认 3000/8000 端口 FREE
   ```powershell
   netstat -ano | findstr :3000
   netstat -ano | findstr :8000
   ```
2. 清理 `.temp` 临时脚本
3. 最终统一验证汇报

---

## 完成标准

**三者齐备才算完成**：
1. ✅ **实测通过** — 浏览器实测全绿，含 375px 移动端、console 0 error
2. ✅ **审计 0 漏洞** — 白盒审计 Phase 0~6 通过，无遗留漏洞
3. ✅ **现场清理** — 服务已停、临时文件已清、测试数据已还原

**未达标准的处理**：
- 任何一项未完成，不得宣布任务完成
- 必须继续修复，直到三项全部通过
